## Catchability Summary

The implemented pickle project catches direct source-level uses of dangerous stdlib deserializers:

- yes: `pickle.load(s)`
- yes: `_pickle.load(s)`
- yes: `pickle.Unpickler.load`
- yes: stdlib `shelve` read surfaces, though shelve stub hygiene needs cleanup

It does **not** yet catch most published CVEs at the public consumer API boundary, because those CVEs usually involve a library wrapper that hides pickle internally:

- `numpy.load`
- LangChain FAISS deserializers
- Kedro `ShelveStore`
- LlamaIndex serializers
- pyfory fallback deserializers
- Pipecat serializers
- project-specific endpoint/helper functions

For those, the next workflow step is target-library stub overlays.

## Lean Scope Result

No new Lean proof is required for "wrapper returns `Unsafe[Any]`" cases. They are new instances of the same source-to-sink quarantine theorem.

New proof work is required only if falcon wants to claim load-time RCE prevention, for example:

- `pickle.loads : TrustedBytes -> T`
- `pickle.load : TrustedReadable -> T`
- `numpy.load : TrustedPath -> T` when pickle/object-array loading is possible

The current implementation proves/demonstrates returned-value quarantine, not that untrusted bytes can never reach `pickle.load(s)`.
